# lip 的工作原理

读完本页，你就会知道：向 lip 提出要求时，它对服务器文件夹做了什么；为什么一次更改可以放心取消；lip 的后台进程有什么用；以及为什么有些事命令允许而界面拒绝。日常使用 lip 并不需要了解这些，但在遇到意料之外的情况时，它们会很有帮助。

## 工作区

**工作区**是存放单个服务器的文件夹。在命令行中，它是你当前所在的文件夹；在界面中，它是当前工作区，即你在界面里选中的文件夹。

工作区里有两类内容：

- **服务器**：游戏、加载器、你的模组、世界和设置。这些都是普通文件，放在游戏期望的位置。
- **`.lip/`**：lip 记录的关于这个文件夹的信息。

| `.lip/` 里的 | 是什么 |
| --- | --- |
| `state.json` | 已安装包的列表：每个包的版本、来源、是否由你主动安装，以及它安装的文件。见[状态文件](state_file.md)。 |
| `config.toml` | 这个工作区的设置。见[配置](../guides/configuration.md)。 |
| `lock` | lip 更改工作区期间占用的文件。 |
| `server.lock` | lip 运行服务器期间占用的文件。 |
| `journal` | 正在进行的更改的记录。只在更改期间或更改被中断后存在。 |
| `logs/` | 失败报告。 |
| `wine/` | 在 Linux 和 macOS 上，服务器的 Wine 前缀。 |

lip 对一个服务器的全部了解都保存在它的文件夹里。移动或复制文件夹，服务器就跟着走。工作区不依赖任何注册表或中央列表；唯一的例外是界面显示的文件夹列表，那只是为了方便。

各个文件的详细说明见[文件和目录](../reference/files.md)。

## 游戏、加载器、模组和依赖

lip 安装的一切都是**包**：一组文件，外加一份说明文件 [`lip.toml`](lip_toml.md)，其中写明了文件放置的位置，以及这个包还需要什么。包在工作区里扮演四种角色：

| 角色 | 是什么 | 数量 |
| --- | --- | --- |
| **游戏** | 某个版本的 Minecraft 基岩版专用服务器（Windows 版或 Linux 版），由 lip 从 Minecraft 官方网站下载。 | 最多一个 |
| **加载器** | LeviLamina，用于改造游戏，使其能够加载模组。仅用于 Windows 服务器。 | 最多一个 |
| **模组** | 由 LeviLamina 加载的包，安装在 `mods/<名字>/`。 | 任意多个 |
| **依赖** | 其他包所需的包。 | 按需 |

由此得出两条规则。

**游戏和加载器是模组立足的地基。** 每个加载器版本都写明了它支持哪些游戏版本，每个模组也写明了自己需要什么。因此，`lip install` 和 `lip update` 不会改动游戏和加载器，只会寻找与之匹配的模组版本。只有安装服务器时（即运行 `lip setup`，或在 `lip install` 中点名指定 LeviLamina 或游戏本身），才会更换地基，并随之把所有模组换成与新地基匹配的版本。

**lip 记得你要求过什么。** 你点名安装的包属于你：在你卸载之前，它会一直保留。而依赖之所以存在，只是因为有其他包需要它；一旦没有包需要，lip 就会将它移除。

每个包都拥有自己安装的文件。两个包不能拥有同一个文件，lip 也绝不删除不属于任何包的文件。只有一个例外：包可以声明自己留下的一些东西，以便在移除该包时一并清理。游戏包对它的某些文件夹就是这样处理的。见[更换游戏后保留什么](../reference/files.md#更换游戏后保留什么)。

## 操作

一次**操作**是对工作区的一次更改，涵盖一条 `lip setup`、`lip install`、`lip update` 或 `lip uninstall` 命令所做的一切，包括它添加或移除的每个依赖。一次操作要么完整执行，要么完全不发生。

操作分为以下步骤：

1. **加锁。** lip 占用 `.lip/lock`。如果另一个 lip 进程正占着它，操作会立刻失败。这样两次更改绝不会混在一起。
2. **恢复。** 如果之前有操作被中断，lip 会先把遗留状态理顺。
3. **决定。** lip 读取已安装的内容，联网查询可用版本，选出一组彼此匹配的包并下载，然后检查每个文件是否都能妥善放置。到这一步为止，工作区里还没有发生任何变化。大多数失败都发生在这一步，此时工作区原封不动。
4. **准备系统。** 如果需要运行 Windows 程序，lip 会确保当前系统能够运行它们。
5. **更改。** lip 删除和写入文件，并运行包要求执行的程序。每次更改前，它都会先在 `.lip/journal` 里记上一笔。被替换或删除的文件会先改用隐藏名称，保留在原位置旁边。
6. **提交。** lip 写入新的 `state.json`，将日志标记为完成，然后删除暂存一旁的旧文件和日志。
7. **解锁。**

![模组页面上有一个标题为“卸载 github.com/LiteLDev/LegacyMoney”的对话框。它列出将要发生的事：卸载 LegacyMoney 0.16.1 和 LegacyRemoteCall 0.13.0。标注 1 指向计划，标注 2 指向“应用”和“取消”按钮。](/screenshots/zh-Hans/plan-01-changes.svg)

在界面里，点击“应用”之前看到的计划就是第 3 步的结果，生成该计划不会对工作区做任何更改。

### 撤销

因为每次更改都是先记录再执行，而且旧文件都会保留到最后，所以 lip 随时都能回退：

- 更改过程中**某一步失败**：lip 按相反的顺序撤销更改，工作区和 `state.json` 恢复原样。
- **你取消了**，用 Ctrl+C 或界面里的“取消”：同上。
- **lip 被杀掉，或者断电**：日志依然留在磁盘上。下次在该文件夹里执行操作或运行 `lip run` 时，lip 会读取日志。如果上次操作已经走到了提交阶段，lip 会把剩余的清理工作做完；否则就撤销上次操作。

只有一样东西无法撤销：包的程序在运行期间做过的事。我们要求包作者将这类程序编写为即使重复运行也无害。

操作失败时，终端或对话框里会给出说明，并生成完整的日志记录。见[故障排查](../guides/troubleshooting.md)。

## 试运行

**试运行**是在第 5 步之前停下的操作。加上 `--dry-run` 参数就能执行试运行；界面在每次执行更改前也会先做一次试运行，以便向你展示执行计划。

试运行提供以下保证：

- 不更改任何文件：无论是工作区、缓存还是设置里的文件，一概不改。
- 不运行任何程序，也不往系统里安装任何东西。
- 不提问。正式操作中会提问的地方，它只说明这里会提问。
- 不加锁，因此既不会等待其他 lip 进程，也不会阻塞它们。
- 不修复被中断的操作，只提示存在这样一次操作。

试运行会完整执行第 3 步中的所有工作，包括联网和下载，因此它给出的就是工作区在当前状态下的真实执行计划。

用法见[试运行](../guides/managing_packages.md#试运行)。

## 守护进程和客户端

运行 `lip install` 时，真正干活的并不是你直接启动的那个程序。你启动的程序是**客户端**，它负责把请求转交给后台的**守护进程**，再把守护进程的反馈显示给你。

守护进程的存在有两个原因：

- **让服务器比终端活得久。** 隶属于某个终端的进程会随终端一起结束。守护进程不属于任何终端，因此由它启动的服务器可以一直运行下去。
- **共享同一个视图。** 无论在哪个终端里打开界面，它们都与同一个守护进程通信，看到的也是同样的服务器和工作区列表。

你不需要手动管理守护进程：

- **它会自己启动。** 如果后台没有守护进程在运行，执行第一条 lip 命令时会自动启动它。
- **每个用户一个。** 守护进程只允许所属的用户连接：在 Windows 上通过命名管道，在其他系统上通过仅你本人可打开的套接字文件。
- **命令的表现和 lip 直接执行时一样。** 守护进程会在你的文件夹里工作，使用你终端的环境变量，读取你的键盘输入，将结果输出到你的终端，并以相同的退出码结束。按 Ctrl+C 也能传达到它那里。
- **命令之间互不干扰。** 守护进程可以同时执行来自多个终端的命令，每条命令都有各自的文件夹和设置。
- **它会自己退出**：当没有客户端连接、也没有服务器在运行，且持续 10 分钟后，守护进程会自动退出。只要还有服务器在运行，它就绝不会退出。
- **更新之后它会被替换。** 较新的 lip 会请求较旧的守护进程退出，并启动自己的守护进程。

`lip daemon status` 显示它是否在运行，`lip daemon stop` 在它空闲时将它停止。见 [`lip daemon`](../reference/commands/daemon.md)。

### 没有守护进程时

如果客户端无法启动或连接守护进程，或者旧版本的守护进程正忙得走不开，客户端会说明情况，然后自己完成工作。命令执行的操作完全一样，只是无法使用依赖长期后台进程的功能：托管服务器。

见 [lip 自己执行了命令](../guides/troubleshooting.md#lip-自己执行了命令)。

## 托管服务器和服务器锁

服务器有两种运行方式。

| | 普通：`lip run` | 托管：界面，或 `lip run --managed` |
| --- | --- | --- |
| 属于 | 启动它的终端 | 守护进程 |
| 终端关闭时 | 服务器被要求停止 | 服务器继续运行 |
| 它的控制台 | 那个终端 | 每个接入它的客户端，以及每个界面的服务器页面 |
| 谁能停止它 | 那个终端 | 任何已接入的客户端，以及任何界面 |

**托管服务器**是由守护进程运行、不专属于任何人的服务器。客户端可以**接入**它来查看输出、向它输入，之后再脱离，而不会打扰它。守护进程在一个工作区里最多运行一个服务器。

无论服务器以哪种方式运行，运行它的进程都会占用**服务器锁**，即 `.lip/server.lock`。“一个工作区一个服务器”正是靠它实现的：第二次启动时会发现锁已被占用，从而直接失败。即使服务器不是由 lip 自己启动的，lip 也是靠这个锁得知有服务器正在运行。

服务器锁和工作区锁相互独立。运行服务器不会锁住工作区，也不会阻止更改；更改工作区也不需要服务器锁。

见[托管服务器](../reference/commands/run.md#托管服务器)。

## 界面与命令

界面并不是另一个有独立逻辑的程序。你在界面里对包、服务器或 lip 设置做的每项操作，都是在当前工作区运行的一条命令，区别只是输出显示在对话框里而非终端里。命令在两边做的事完全一样。唯一背后没有对应命令的是编辑器：游戏和模组配置文件的编辑器，以及创建和编辑 `lip.toml` 的表单。

界面只在一个地方更谨慎。**当前工作区的服务器运行期间，界面：**

- 不在当前工作区安装、更新、卸载任何内容，也不安装服务器；
- 不保存 `server.properties`、`allowlist.json` 和 `permissions.json`。

它会提示你先停止服务器：

![服务器运行时的模组页面。顶部有一行“服务器运行中，停止后才能更改模组。”某个模组的菜单打开着，其中的更新和卸载项被禁用，原因是“请先停止服务器。”](/screenshots/zh-Hans/mods-04-server-running.svg)

模组的设置依然可以保存，并在下次启动时生效。

无论服务器是通过当前界面、另一个界面，还是在终端里直接运行 `lip run` 启动的，这一限制都会生效。界面通过服务器锁来判断服务器是否在运行。

**命令不会拒绝。** 服务器运行时，`lip install` 照常执行，而且无论结果如何，更改都是安全的。如果某个文件因被运行中的服务器占用而无法替换，操作就会失败并回滚；如果成功，更改会在下次启动服务器时生效。

| 服务器运行期间 | 界面 | 命令 |
| --- | --- | --- |
| 安装、更新、卸载、安装服务器 | 拒绝 | 允许。可能因文件被占用而失败，此时会自动撤销。 |
| 编辑游戏的设置 | 显示但不保存 | lip 没有相应的命令，请直接编辑文件。 |
| 编辑模组的设置 | 允许 | 同上。 |
| 查看已安装的内容 | 允许 | 允许 |

还有一点不同：界面会将服务器作为托管服务器启动，而不带 `--managed` 的 `lip run` 不会。

页面与命令的完整对应关系见[界面参考](../reference/interface.md)。

## 用户目录

在工作区之外，lip 为每个用户保留四个目录。

| 目录 | 存放内容 | Windows | Linux 和 macOS |
| --- | --- | --- | --- |
| 配置 | 你的设置文件 `config.toml` | `%APPDATA%\lip` | `$XDG_CONFIG_HOME/lip`，默认 `~/.config/lip` |
| 缓存 | 从网络下载的文件，保留以免重复下载 | `%LOCALAPPDATA%\lip\Cache` | `$XDG_CACHE_HOME/lip`，默认 `~/.cache/lip` |
| 数据 | lip 为运行服务器而安装的组件：Linux 和 macOS 上是自带的 Wine，Windows 上是 Visual C++ 运行库 | `%LOCALAPPDATA%\lip\Data` | `$XDG_DATA_HOME/lip`，默认 `~/.local/share/lip` |
| 状态 | 界面的工作区列表 `workspaces.json` | `%LOCALAPPDATA%\lip\State` | `$XDG_STATE_HOME/lip`，默认 `~/.local/state/lip` |

这些目录的清理说明：

- **缓存**：随时可以清理（运行 `lip cache clean`）。需要时 lip 会重新下载。
- **数据目录**：没有 lip 进程运行时可以删除。需要时 lip 会重新安装 Wine 或 Visual C++ 运行库。
- **状态目录**：没有 lip 进程运行时可以删除。删除后只会清空界面里的文件夹列表，不会删除文件夹本身。
- **配置目录**：只存放你的设置。

在 Linux 和 macOS 上，守护进程的套接字位于 `$XDG_RUNTIME_DIR/lip`；若未设置该变量，则位于状态目录中。在 Windows 上，守护进程使用命名管道，不生成文件。

除了上述目录、套接字所在目录、工作区以及你指定的路径外，lip 只会在执行 `lip self-update` 替换自身时写入自己的安装目录。它不使用系统的临时目录。
